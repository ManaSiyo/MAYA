AUGUST 16, 2026, MORNING. STATUS: OPEN, WAITING ON FROMSA. RECURRED.

Symptom: Systems Map says "something needs attention (Drive authorization
rejected, submissions will not land)" and Latest Submissions is empty. This is
the second death of the same credential: it was renewed August 13 at 3:55 PM
and it was dead again by August 16.

What was ruled out today: the map code is fine (v13.23 is live, the page loads,
every other light is green), and the deploy did not overwrite anything, because
cloudbuild.yaml sets no environment variables at all. The server is simply being
told no by Google when it exchanges the refresh token.

Why a token minted "In production" can still die in three days: the token is
revoked, not expired. The usual causes, in order of likelihood: the OAuth
consent screen was moved back to Testing, or the app is unverified and using
sensitive Drive scopes, or the atelier Google account's password was changed, or
too many tokens were minted for the same client and account so Google revoked
the oldest ones, or someone removed MAYA under the account's third party access.

What Fromsa must do, in this order:
1. Check the consent screen status and audience for project pro-maya.
   https://console.cloud.google.com/auth/audience?project=pro-maya
   If it says Testing, press Publish app. Testing kills a token every 7 days.
2. Check that MAYA still has access under the atelier account.
   https://myaccount.google.com/connections
3. Mint a fresh refresh token in the OAuth Playground with the SERVER's client
   pair (the one in Cloud Run, not the sign-in client), full drive scope,
   signed in as the atelier Drive account. https://developers.google.com/oauthplayground
4. Put it into GOOGLE_OAUTH_REFRESH_TOKEN and deploy a new revision.
   https://console.cloud.google.com/run/detail/us-west1/maya-api/revisions?project=pro-maya
5. Reload the Systems Map, signed in, and confirm Drive turns green and the
   submissions appear. Then log the result here.

Until then the site works, generation works, and only Drive submissions are
blocked.

AUGUST 14, 2026, NIGHT. STATUS: FIXED IN CODE v13.19-v13.23, NOT YET DEPLOYED;
DRIVE CREDENTIAL MUST STILL BE VERIFIED AFTER DEPLOY.

Symptom: Systems Map appeared missing or slow, Latest Submissions reported that
Drive was not answering, Community could retain stale/ghost cards, and project
work performed during a sign-out/sign-in boundary could theoretically land in
the next account.

Cause: status waited on serial image probes before starting API health; Drive
requests had no hard provider timeout and rebuilt too many folder details on
every refresh; Community polled and keyed repaint only by post id; generation
provenance was inferred from card shape; queued project saves resolved the
Firebase uid at commit time instead of capturing the initiating account.

Fix: parallel health checks, bounded Drive calls and short submissions cache;
realtime Community listener, URL-aware repaint, actual image-model provenance
and gpt-image-2-only client/rules gates; all project reads/writes/uploads pinned
to their starting uid with serialized auth teardown and awaited Firebase
sign-out. Fabric assets are lazy, OpenAI responses stream, all Drive operations
have bounded waits, and deep health tells a timeout from rejected credentials.

Operational truth: an OAuth `invalid_grant` cannot be fixed in source. If the
signed-in deep health result is red after v13.23 deploys, renew
`GOOGLE_OAUTH_REFRESH_TOKEN` on Cloud Run using the production Drive OAuth
client and record that owner-run action here.

AUGUST 14, 2026, AFTERNOON. STATUS: FIXED IN v13.15-v13.18.

Symptom: Systems Map could claim all green while Drive had not been checked,
older refreshes could overwrite newer results, and rapid account/project work
could leave ghost wall pictures or deleted Storage objects behind.

Cause: public health treated "configured" as "working"; async status requests
had no generation guard; project deletion discarded its Storage retry list;
My Fabrics removed its cloud index before a one-shot Storage delete; wall
updates could keep valid ownership while changing their project id.

Fix: timed and sequenced status checks plus immediate deep health after sign
in; atomic project/tombstone/wall/share deletion; durable project and fabric
cleanup queues; immutable wall uid/pid on update. Community and favorites
visual changes are covered in the browser regression assertions.

AUGUST 13, 2026, AFTERNOON. STATUS: FIXED, 3:55 PM.

Symptom: Systems Map Drive light red, no submissions listed, community
wall empty (the wall turned out to be unrelated, see below).

Root cause, confirmed at 3:05 PM by calling /api/admin/submissions with
Fromsa's own signed in session: the env vars ARE set (healthz reports
drive configured), but Google answers the token exchange with
  oauth refresh 400 invalid_grant: "Token has been expired or revoked."
The GOOGLE_OAUTH_REFRESH_TOKEN on Cloud Run is dead.

Why it keeps dying: if the OAuth consent screen for the pro-maya web
client is in Testing publishing status, Google expires every refresh
token after 7 days. The token was renewed August 5. August 5 plus 7 days
is August 12. It died on schedule. It will die every week until the app
is published to Production.

The fix, two parts, both in Fromsa's hands (credentials):
1. PERMANENT: console.cloud.google.com, APIs and Services, OAuth consent
   screen, project pro-maya. If Publishing status says Testing, press
   Publish app. This stops the weekly expiry.
2. NOW: mint a fresh refresh token for the atelier Drive account (same
   procedure as August 5, see docs/server/MIGRATION-RUNBOOK.md), then
   Cloud Run, maya-api, Edit and deploy new revision, replace
   GOOGLE_OAUTH_REFRESH_TOKEN with the new value, deploy.
What was actually done, 3:40 to 3:55 PM: confirmed the OAuth app was
already In production (so the weekly expiry only applied to tokens
minted earlier, under Testing). Retrieved the server's real client pair
from the Cloud Run environment variables (the first client edited in
the Auth console turned out to be the sign in client, not the Drive
one). Minted a fresh refresh token in the OAuth Playground using that
pair with the full drive scope, signed in as the atelier Drive account,
pasted it into GOOGLE_OAUTH_REFRESH_TOKEN, deployed a new revision.

Verified immediately from Fromsa's signed in session:
/api/admin/submissions answered 200 with 7 submissions, and
/api/healthz/deep answered ok true, drive true. Tokens minted under In
production status do not expire on a clock; this should not recur
weekly. If it EVER recurs, check first whether someone pressed Back to
testing on the Audience page, or changed the atelier account password
(that revokes refresh tokens).

Also fixed in code (v13.5): the Systems Map used to show "waiting for
the one sign in" when this failure happened. It now prints the real
error, so next week cannot masquerade as a sign in problem.

Separately confirmed the same afternoon: the community wall is NOT a
Drive or rules problem. A full pipeline self test (Storage upload,
Firestore create, read back, delete) passed from Fromsa's own session.
The wall is empty because publishing only happens at the moment a heart
is toggled, and every existing heart predates the wall. Re-heart any
vision and it publishes.
